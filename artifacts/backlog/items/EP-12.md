## What

`npm run mutation-check` reports six attacks. Inside the CI container two of them never run: they
report `SETUP FAILED — mutation target not found` and the stage exits 1. The property this epic owes
is that every mutation check the repository advertises genuinely reaches and falsifies its intended
gate in the container, or is not advertised.

## Why

A gate that reports it did not run is better than one that lies, and this one is honest about
failing. What it is not honest about is the shape of its own coverage: `README.md:153` describes the
command as attacking each gate, and two of the gates it names — inventory and fidelity, the two that
protect the spec-to-standards chain — have never been attacked in the environment the repository
treats as authoritative. The mutation checks exist because the framework's own doctrine is that a
check nobody attacked is an assertion. Two of them are currently that.

## Notes

**The byte-level cause, measured on 2026-08-23 at `85b27b7`, before any fix was proposed.**

The container's tree is not the committed tree. Measured with Node — not with the MSYS `grep`/`cat`,
which strip CR on read and report LF for files that hold CRLF, and which is why an earlier pass of
this diagnosis reached the wrong answer:

| file | committed blob | developer checkout | fresh `git worktree` export | image `/repo` |
|---|---|---|---|---|
| `artifacts/prompts/mathematics-standards-spec.md` | LF | LF, 14 315 chars | **CRLF**, 14 703 | **CRLF** |
| `standards/20-must-never-rules.md` | LF | LF, 11 009 | **CRLF**, 11 167 | **CRLF** |
| `rules/claims.json` | LF | CRLF | CRLF | CRLF |

The deltas are exactly the line counts — 14 703 − 14 315 = 388 = the file's line count; 11 167 −
11 009 = 158, likewise — so this is whole-file LF→CRLF conversion and nothing else.

The conversion happens at **worktree export**, not at image build. `core.autocrlf` is `true` here, and
`.gitattributes` pins `eol=lf` only for `*.sh`, `Dockerfile*` and `*.yml`. `scripts/ci.mjs:199` builds
the image from a throwaway `git worktree add --detach` of the SHA, and that checkout converts every
other text file. The two mutators that fail are exactly the two whose search strings are anchored on
`\n` (`scripts/mutation-check.mjs:78-79`, `:87-88`); the four that pass either search a string with no
newline in it (`"id": "claims.silent-promotion"`) or operate on files the conversion does not disturb.
`mutate()` reads the file and tests `original.includes(from)` before writing anything, which is why
the symptom is `SETUP FAILED` and not a write error.

**Why it passes natively and fails in the container, which is the reverse of the intuition.** The
developer checkout holds LF for those two files — they were written by tooling and never
re-materialised by git — so `npm run mutation-check` sees LF and all six pass. The container sees a
*pristine* export, which is the CRLF one. The native run is the anomaly; a fresh clone on this machine
would fail the same way the container does.

**The finding underneath the finding.** `Dockerfile.ci` states that the image is a sealed snapshot of
the commit, and `compose.ci.yml` that the build context is "a throwaway git worktree containing
exactly the commit under verification". For every text file without an `eol` attribute that is false
by one byte per line. Nothing observed depends on it beyond these two mutators, and the pipeline is
not thereby invalid — but a fix that only teaches the two mutators to tolerate `\r` would leave the
stated invariant untrue, so the choice between repairing the export and repairing the mutators is a
decision this epic has to make explicitly rather than absorb.

**Two claims in the first draft of this item were wrong, and the falsifiers are what said so.**
Before implementing anything, four falsifiers were written and run against `main` (5afcd00). Two went
red for the recorded reason and two went green, because the defects they were written for do not
exist:

| falsifier | against `main` | |
|---|---|---|
| a tracked LF blob becomes CRLF in the exported/container tree | **RED** | 257 of 286 tracked files |
| each of the mutation checks fails to reach its gate | **RED** | 2 of 5 targeted mutations miss |
| mutation execution modifies `/repo` instead of a disposable copy | GREEN | the mutating stage runs in `/work` |
| `/repo` is writable despite the documented read-only boundary | GREEN | a write to `/repo` returns `EROFS` |

The first draft of this item said the `/work` copy existed nowhere in the code. It exists — in
[`scripts/ci.mjs`](../../../scripts/ci.mjs), which composes the container command as
`cp -r /repo/. /work/ && cd /work && exec node scripts/run-stages.mjs`, not in `run-stages.mjs`,
which is the only file the first pass grepped. It is also already regression-tested, twice, in
`test/local-ci.test.mjs`. Recorded rather than quietly deleted: the reading was wrong, the mechanism
was sound, and the second and third findings of that draft should not survive as folklore.

What remains true is the first finding, and it is the larger one.
