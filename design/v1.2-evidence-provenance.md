# v1.2 — Tier 2: evidence provenance

**Milestone claim.** *Every result must be able to say what evidence surface it inspected, and whose
repository that evidence belongs to.*

Tier 1 asked how strong a finding's evidence was. Tier 2 asks a prior question the framework has
never asked: **was there any evidence at all, and was it the adopter's?** Tier 1 constrained what a
finding may conclude; this constrains what a *pass* may claim.

Scope: `§0` (data sufficiency), `§0e` (attestation currency), `§0h` (whose property), `§0m` (a rule
that accepts a pointer must follow it). Disposition tier 2, "false assurance".

Base: `03f44d6`, the Tier 1 endpoint. Branch `tier2-evidence-provenance`, worktree
`../MathematicsStandards.tier2`. **Tier 1 stays frozen at `03f44d6`** — it is the acceptance baseline
this milestone is measured against, and a baseline edited during the next change is not a baseline.

---

## 1. The measurement this milestone starts from

Both frozen adopters, run at `03f44d6`, every result's `evidence` array:

| | RH | PvsNP |
| --- | --- | --- |
| `passed / evaluated` (a detector said so) | 48 | 51 |
| …of those, naming any evidence | **0** | **0** |
| `passed / attested` (a human said so) | 12 | 0 |
| …of those, naming any evidence | 12 | — |

**Not one machine-produced pass in either repository names a single file.** The only passes that say
what they rest on are the ones where a person wrote the paths down by hand, in
`reviewedAgainst.paths`. The framework's automated assurance is, at the level of the record, entirely
unsourced — and it is the automated half that produces 99 of the 111 passes.

This is the substrate defect. `§0`, `§0h` and `§0m` are three ways of exploiting it:

```text
§0    the surface was empty          → a pass over nothing
§0h   the surface was the framework  → a pass over someone else's property
§0m   the surface was the wrong one  → a pass over a thin proxy, blind to the real artifact
```

All three are invisible for the same reason: **the result does not record which surface it read.**
Fixing them individually would produce three special cases and leave the fourth instance, whatever it
turns out to be, equally invisible. So the substrate goes first, and the three repairs become
consumers of it.

### The mechanism, precisely

`evaluated` — the input the whole no-false-green invariant rests on — is a **static array of rule
ids** (`scripts/evaluated.mjs`, 53 entries). It is a claim made at authoring time that a detector
exists, and it is read at run time as though it were a claim that the detector had something to look
at. `compliance.mjs:129` is where the two are conflated:

```js
if (hits.length === 0 && (rule.validationType === "manual-review" || !examined.has(rule.id))) → skipped
if (hits.length === 0)                                                                        → passed
```

`examined` answers *is there a check for this rule?* Nothing anywhere answers *did the check have a
subject?* That is `§0`'s "detector availability versus data sufficiency" stated as a line number.

The equivalent gate inside the detectors is `if (!ledger) return;` — sixteen occurrences covering 27
rules. A detector that returns early is indistinguishable, downstream, from one that ran and found
nothing. Both produce zero findings, and zero findings is read as compliance.

## 2. The model

One new result field. It is the whole design.

```jsonc
"inspected": {
  "subject": "project",              // or "framework" — whose property this result is about
  "state": "inspected",              // inspected | no-subject | unresolved-pointer
  "surfaces": [
    { "surface": "claims-ledger", "paths": ["artifacts/claims-ledger.md"], "declared": false }
  ]
}
```

**Surfaces are declared per rule and resolved per run.** A new module states, for each rule with a
detector, which evidence surfaces that rule reads. The CLI resolves each surface against the target
repository to a concrete list of repo-relative paths. The union of a rule's resolved paths is what
that rule inspected, and it goes into the result whether the rule passed or failed.

The surface vocabulary is small and closed, because a surface the framework cannot name is a surface
it cannot check:

| surface | resolves to |
| --- | --- |
| `claims-ledger` | the ledger named by `mathematics.claimsLedger`, if it exists |
| `proof-sources` | proof-assistant files found in the scan |
| `open-problems` | `problem.md` records under `mathematics.openProblemsDir` |
| `project-policy` | `project-policy.yml` |
| `prose` | scanned text files, excluding the framework's own standards documents |
| `references` | the reference block of the ledger |
| `declared:<rule>` | artifacts the adopter named for this rule (see §5) |
| `framework-home` | the framework's own installed artifacts — **subject `framework`** |

`state` is derived, not authored:

- **`inspected`** — at least one surface resolved to at least one path. The rule may pass, fail, or
  warn exactly as it does today.
- **`no-subject`** — every surface resolved empty. The rule becomes `skipped / not-evaluated`,
  carrying a reason that distinguishes it from *no detector exists*. This is `§0`.
- **`unresolved-pointer`** — the adopter declared an artifact for this rule and it does not resolve.
  **Fail-closed** (§5).

### Three decisions, and why

**A rule with no subject is `not-evaluated`, not `failed`.** `§0` says this explicitly and it is
right: a project that has not yet written a claims ledger should see *nobody checked*, not a red
build for every claim rule. The distinction from "no detector exists" is carried in the reason
string, not in a fourth disposition — inventing one would break every consumer switching on
`disposition`, to record something the reason already says.

**`no-subject` leaves the score's denominator, exactly as `not-evaluated` already does.** No new
scoring rule; the existing one does the right thing once the status is right. Scores will move, and
that movement is the acceptance signal, not a regression.

**`subject: "framework"` is recorded, and in this step changes nothing else.** `§0h` says the
requirement is not to exclude these rules — the framework auditing its own integrity during an
adopter's run is useful — but that a result must say whose property it is about. Whether a
framework-subject result belongs in an *adopter's* score is a real question and it is deferred to
step 5, where it can be decided against a measurement instead of a guess. Recording the subject is
what makes that measurement possible.

### What this is not

It is not a claim that the framework read the mathematics. `inspected` records which files a
detector's evidence came from; it says nothing about whether the check is any good. A rule that reads
the right file and applies a bad regex will now say so precisely — which is an improvement over
saying nothing, and is not assurance.

## 3. The four claims, as tests, before implementation

Red first. Each claim is a property of the output, not of an implementation.

**C1 — a PASS names the project evidence it inspected.** A rule that passes over real evidence
carries a non-empty `inspected.surfaces` with resolved paths. A rule with nothing to read does not
pass at all.

**C2 — wrong-root evidence cannot satisfy an adopter rule.** Pinned as a cross-root pair, both
directions, per the sequencing note below:

```text
framework HOME has valid evidence, adopter does not  →  the adopter must not PASS
adopter has valid evidence, framework HOME does not  →  the adopter may PASS
```

Both directions are required. The first alone is satisfiable by breaking the rule; the pair is
satisfiable only by moving the subject of evaluation from framework-global state to project state. A
changed path constant passes the first and fails the second.

**C3 — an accepted pointer must resolve to and inspect its target.** A declared artifact that does
not exist fails closed. A declared artifact that exists is *read*: the syntactic presence of the
pointer never satisfies the rule on its own.

**C4 — `audit` declares whether a verdict was computed.** See §6.

Each red test must fail against `03f44d6` for the stated reason, and the reason is recorded beside it
— a test that fails because a fixture is malformed proves nothing about the claim.

## 4. `§0e` — the recorded mechanism is wrong, and the correction belongs here

The candidate says the validator does not report the current digest, citing all three output
surfaces. **Measured against the frozen RH specimen, that is not what happens.**

| surface | occurrences of a current attestation digest |
| --- | --- |
| human render (`validate`) | **14 of 14** |
| `status` | 0 |
| `--json` | 0 |

RH has 14 attestations, all with `reviewedAgainst.paths`, none with a `digest`.
`attestationDigests` computes a digest for every one of them, and `standards.mjs` prints all 14 — in
the `else` branch, reached only when neither `--json` nor `--status` is set.

RH's own `project-policy.yml` records the opposite in a standing comment: *"the validator reports the
current digest; it does not, so there is nothing to copy."* The adopter measured from `--json`. They
were right about their own observation and wrong about the mechanism, and the recorded consequence —
14 permanently-fresh attestations — is exactly as real either way.

**The correction makes the defect more clearly this milestone's.** It is not that the digest is never
computed or never shown. It is that a value which exists, is correct, and is the documented way to
opt into staleness detection is emitted on exactly one of three output surfaces — and not the
machine-readable one. That is a visibility defect in the same family as `§0`, `§0h` and `§0m`, and it
is why `§0e` is in this milestone rather than beside it.

The candidate entry will be corrected in place with the measurement, not rewritten: a mis-stated
mechanism whose consequence held is itself evidence about how these defects get found.

## 5. Pointers as a reusable primitive

`§0m` must not be repaired inside `lifecycle.failed-routes-preserved`. The primitive:

```js
resolveEvidencePointer(projectRoot, pointer)
  → { kind: "resolved",   pointer, paths: [...] }
  → { kind: "unresolved", pointer, reason }
  → { kind: "unsupported", pointer, reason }
```

`unsupported` is not a convenience. A pointer form the framework does not understand — a URL, a glob
it does not implement, a reference into another repository — must be reported as *not followed*,
never silently treated as absent (which would read as `no-subject`) and never as satisfied.

Where pointers come from: the adopter names them, per rule, in the policy. A declared pointer is a
positive assertion by the adopter that a specific artifact discharges a specific duty, and it is
therefore held to a higher standard than an absence:

```text
declared and resolves      → the detector reads the named artifact
declared and unresolved    → FAIL (fail-closed). The adopter asserted an artifact that is not there.
declared and unsupported   → FAIL. The framework must not claim to have followed what it cannot read.
not declared               → fall back to the existing heuristic, unchanged
```

The fail-closed cases are failures rather than `no-subject` for a reason worth stating: `no-subject`
is the honest report when nobody claimed anything. Here somebody did.

**A pointer's existence must never satisfy the rule.** This is the specific defect `§0m` records —
`lifecycle.failed-routes-preserved` passes on a `###` heading in `problem.md` while blind to PvsNP's
1,283-line `docs/FAILED_ATTEMPTS.md`. Replacing "guess from the path" with "accept whatever is
declared" would reproduce the defect with better manners.

## 6. `audit`'s contract, decided rather than drifted

`audit` emits findings and no verdict. **That is intentional and stays**, on the evidence of the
framework's own design: `renderHuman` ends with *"This is evidence, not a verdict. Run
`math-standards validate` for a compliance status."* The separation is the point — observations and
conclusions are different artifacts, and collapsing them would undo a distinction this framework
exists to draw.

The defect is that the intent is stated **only in the human render**. `audit --json` emits
`{schemaVersion, repo, auditedAt, findings}` and nothing that says a verdict was not computed. A
consumer that receives it has no field distinguishing *"audited, no verdict"* from *"evaluated, and
nothing to report"*. An empty `findings` array reads as a clean bill of health.

So: make the declaration machine-readable and unmistakable, in both directions.

```jsonc
{ "schemaVersion": "1.0.0", "repo": "...", "verdict": null, "verdictComputed": false,
  "note": "Audit only — no compliance verdict was computed. Run `validate` for one.", "findings": [] }
```

Additive; `schemaVersion` unchanged, on Tier 1's reasoning — the format versions on incompatible
change, and a new field breaks no consumer joining on `findings`.

## 8. Predictions

Written before implementation. Recorded so the measurement can falsify them.

| | Predicted |
| --- | --- |
| RH `passed / evaluated` | **falls sharply.** 48 passes with no named evidence; RH's ledger holds 11 claims against 987 declarations, so many claim rules read a real but thin subject — those still pass. The vacuous ones are the 23 the baseline already identified |
| PvsNP `passed / evaluated` | **falls.** By how much is genuinely unknown, and this is the more informative specimen: PvsNP's ledger is real and curated, so a large fall here would mean the surface model is too coarse, not that the passes were vacuous |
| Either adopter's verdict | **must not improve.** A milestone about false assurance that makes a repository look more compliant has failed |
| RH `BLOCKED_BY_INVARIANT` | **unchanged.** Its two blockers are rejected attestations, untouched by anything here |
| PvsNP `NON_COMPLIANT` | **unchanged, or blocked.** The two findings are detector findings over real evidence; if either turns out to rest on an empty surface it becomes `no-subject`, which would remove a *finding* — and a removed finding must be explained, not welcomed |
| `integrity.*` on both | **`subject: "framework"`**, still passing, no longer indistinguishable from a statement about the adopter |
| `lifecycle.failed-routes-preserved` | **passes in both, for the first time on the right artifact** — RH's `Research/FAILED_APPROACHES.md`, PvsNP's `docs/FAILED_ATTEMPTS.md`, once declared |

The uncomfortable prediction is the last: this milestone makes both repositories score worse without
either changing. That is the correct direction. A score computed over rules that examined nothing was
never a measurement of the project.

## 9. Standing test rule, carried out of Tier 1

Tier 1 found a test asserting "the prose arm must not block" that passed against a run returning
`NOT_EVALUATED` — it counted blockers, and zero blockers is what a verdict-less run has. The
assertion was true and vacuous.

> **No acceptance assertion may rely solely on an aggregate count when it can name the rule and the
> status directly.** Counts are permitted in addition to a named assertion, never instead of one.

Recorded in `design/testing-principles.md`. It is broader than this milestone and it is stated here
because this milestone is where it will next be violated: every claim in §3 is naturally expressible
as a count, and a count is exactly what a `no-subject` state changes for reasons unrelated to the
claim under test.
