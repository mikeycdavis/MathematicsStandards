## What

This repository states two incompatible answers to one question, both deliberately, in two places a
reader would treat as authoritative.

`rules/evidence.json` — the published description of `evidence.artifact-linked`:

> Every path-shaped evidence reference resolves to a file in the repository, **with any anchor suffix
> removed before resolution.**

`scripts/pointers.mjs:97-102` — the resolver, refusing to do exactly that:

> `'…'` names a fragment within a file. Fragment resolution is not implemented, and reading the whole
> file instead would inspect something other than what was declared.

and, in the comment above it:

> a rule told to inspect one section of a document and handed the whole document has not inspected
> what it was pointed at.

The consequence for adopters is that a ledger locator naming a location that does not exist is
reported as resolved, and counted in `inspected.surfaces` as an inspected artifact, provided the
containing file exists. `resolveEvidencePointer` — the careful surface — has two callers, both on the
policy-declared failed-routes path, so **no ledger locator reaches it**. The surface adopters' ledgers
actually travel is the one that widens.

## Why

**Reproduced on `main@8e77453`, 2026-08-26**, during FE-42's red-first design check. One character
changed in a copy of the `math-compliant` fixture:

| ledger cites | file exists | anchor exists | `evidence.artifact-linked` | verdict |
|---|---|---|---|---|
| `proofs/clm-0002.md#no-such-section` | yes | **no** | **passed** | **`COMPLIANT` / 100** |
| `proofs/no-such-file.md#no-such-section` | no | no | failed | `NON_COMPLIANT` / 95 |

So the file arm works and the fragment arm is discarded. A full score, over evidence one of whose
locators names a location that is nowhere in the cited document.

This is EP-07's subject rather than a missing capability: a surface reporting resolution it did not
achieve. It is also the unfinished remainder of §0m — [FE-20](FE-20.md), *a rule that accepts a
pointer must be able to follow it* — which built the careful resolver but did not put the ledger
consumers through it.

## Notes

**This is a published-contract reconciliation, not unfinished FE-42 work.** [FE-42](FE-42.md) fixed
inconsistent locator *handling* and misleading *reporting*: four file-level consumers now share one
primitive and the fifth stopped comparing an unnormalised value. Every one of those changes preserved
the published anchor-stripping semantics, deliberately and by instruction. The falsifier above was
carried through FE-42 as a **red measurement, kept red**, precisely so it would not be resolved by a
repair that had no mandate to redefine a contract.

**Nor is it an EP-08 representation gap.** EP-08 is about vocabulary the framework cannot express.
This framework can express both answers; it has published one and implemented the other in a module
that says why. The defect is the disagreement, not a missing state.

**The anchor-stripping clause is original, not an accident.** It is present in the first commit that
created the catalog, `168fcd3`, and under this repository's catalog-before-evaluator ordering it was
written before the detector existed. It cannot be dismissed as a description someone later wrote to
match the code, and it must not be quietly reinterpreted as a bug. Whatever is decided, the decision
has to be made against the sentence as published.

### The design question, to be answered before any code

> **Does a published evidence locator contract mean "the containing file must exist," or "the named
> location must resolve," and what compatibility/release consequence follows from changing that
> answer?**

**A design record now exists.** [design/fe-44-locator-contract.md](../../../design/fe-44-locator-contract.md)
evaluates six models — the five below plus one the item does not list — against the written standards
and the compatibility contract, and recommends one. It is a recommendation, not a decision: this item
stays `READY`, and nothing in `rules/`, `standards/`, `scripts/pointers.mjs`, or any detector has been
touched.

**Deliberately not answered here.** The defect is confirmed; the model is not. Both readings are
defensible and they are not the same feature:

- *Containing file must exist* is what is published today. It keeps every existing adopter ledger
  valid and leaves the false-assurance measurement above standing as accepted behaviour, which would
  then need saying out loud in the rule's `$assuranceNote` rather than left implicit.
- *Named location must resolve* is what `pointers.mjs` argues for. It would turn some currently
  `COMPLIANT` adopter repositories `NON_COMPLIANT` without any change to their evidence, which is a
  compatibility event for consumers of the verdict, not only of the format.

Intermediate models exist and should be weighed rather than assumed away — resolving the anchor and
reporting an unresolved fragment as `not-evaluated` instead of a failure; a distinct evidence state
for *the document was inspected, the named location was not found*; or making it a separate rule at a
lower severity so the existing rule's contract is left intact.

### Release-bearing

**If the published rule description changes, this carries a release boundary**, and the item may not
be implemented as though it were a bug fix. `CHANGELOG.md` decides releases by what happens to rules —
removing, weakening, or reclassifying any rule is MAJOR — and rewriting what a rule promises is that
kind of act. The "versions the format on incompatible change" clause is the one that classified 3.0.0,
and a verdict moving from `COMPLIANT` to `NON_COMPLIANT` on unchanged adopter evidence is at least as
consequential to a machine consumer as the field-domain widening that release was about.

The lifecycle fields exist for this: a rule that changes meaning may need `deprecatedIn` /
`supersededBy` rather than an edited description, which is one of the arms protecting
[Standard 21](../../../standards/21-standards-integrity.md) and is itself part of the design question.

### In review

`IN_REVIEW`: the design landed as [design/fe-44-locator-contract.md](../../../design/fe-44-locator-contract.md)
and the recommended model is implemented on a measured branch. Falsifiers D1-D7 were written first
and were red on `1153092` for the reasons the design record predicts — D1 and D6 because the
inspection record was byte-identical across a resolvable and an unresolvable anchor, D5 because the
new rule did not exist — while D2, D3, D4 and D7 were green throughout as preservation guards. The
published description, `level`, `severity` and verdict semantics of `evidence.artifact-linked` are
unchanged, and no version has been assigned: the release is prepared as MINOR / 3.1.0 under an
Unreleased heading in `CHANGELOG.md`. Every verdict and score across all 32 fixtures is unchanged;
the only movement is the new rule's own row, `no-subject` wherever a ledger carries no anchor.

Two automated review findings arrived on the pull request and were dispositioned from the design
record rather than from the review. **The declared fragment was being slugged before matching**, so a
locator `#a.b` resolved against a heading `A.B` whose only anchor is `ab` — the rule manufacturing a
match for the very thing it exists to report absent. Fixed by comparing the locator as written; the
leniency that removed was unevidenced, since the shipped template teaches the slug form and §3 of the
design record measured zero anchored locators across both frozen adopters. **A ledger mixing a
followable locator with an unfollowable one reports on the followable one** and names the rest in the
inspection record's `reason`. That was not changed: withdrawing the rule because one locator was
unreachable is the granularity error §4 Model 3 is rejected for — "one unresolvable anchor would
withdraw the rule entirely, discarding the existence checks" — so the wording that read as a
per-locator promise was corrected instead, in the `$assuranceNote` and the changelog. Both are pinned
by falsifiers R1 and R2, each mutation-checked against the behaviour it forbids; R2 is the only test
in the suite that catches the reviewer's proposed change. All 29 fixture envelopes are byte-identical
across the repair, and the rule partition stays 10 full / 45 partial / 29 expert-judgement.
