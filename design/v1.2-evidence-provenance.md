# v1.2 — Tier 2: evidence provenance

**Milestone claim.** *Every result must be able to say what evidence surface it inspected, and whose
repository that evidence belongs to.*

Tier 1 asked how strong a finding's evidence was. Tier 2 asks a prior question the framework has
never asked: **was there any evidence at all, and was it the adopter's?** Tier 1 constrained what a
finding may conclude; this constrains what a *pass* may claim.

Scope: `§0` (data sufficiency), `§0e` (attestation currency), `§0h` (whose property), `§0m` (a rule
that accepts a pointer must follow it). Disposition tier 2, "false assurance".

Base: `03f44d6`, the Tier 1 endpoint. Branch `tier2-evidence-provenance`, worktree
`../MathematicsStandards.tier2`. **Tier 1 stays frozen at `03f44d6`** — it is the acceptance baseline
this milestone is measured against, and a baseline edited during the next change is not a baseline.

---

## 1. The measurement this milestone starts from

Both frozen adopters, run at `03f44d6`, every result's `evidence` array:

| | RH | PvsNP |
| --- | --- | --- |
| `passed / evaluated` (a detector said so) | 48 | 51 |
| …of those, naming any evidence | **0** | **0** |
| `passed / attested` (a human said so) | 12 | 0 |
| …of those, naming any evidence | 12 | — |

**Not one machine-produced pass in either repository names a single file.** The only passes that say
what they rest on are the ones where a person wrote the paths down by hand, in
`reviewedAgainst.paths`. The framework's automated assurance is, at the level of the record, entirely
unsourced — and it is the automated half that produces 99 of the 111 passes.

This is the substrate defect. `§0`, `§0h` and `§0m` are three ways of exploiting it:

```text
§0    the surface was empty          → a pass over nothing
§0h   the surface was the framework  → a pass over someone else's property
§0m   the surface was the wrong one  → a pass over a thin proxy, blind to the real artifact
```

All three are invisible for the same reason: **the result does not record which surface it read.**
Fixing them individually would produce three special cases and leave the fourth instance, whatever it
turns out to be, equally invisible. So the substrate goes first, and the three repairs become
consumers of it.

### The mechanism, precisely

`evaluated` — the input the whole no-false-green invariant rests on — is a **static array of rule
ids** (`scripts/evaluated.mjs`, 53 entries). It is a claim made at authoring time that a detector
exists, and it is read at run time as though it were a claim that the detector had something to look
at. `compliance.mjs:129` is where the two are conflated:

```js
if (hits.length === 0 && (rule.validationType === "manual-review" || !examined.has(rule.id))) → skipped
if (hits.length === 0)                                                                        → passed
```

`examined` answers *is there a check for this rule?* Nothing anywhere answers *did the check have a
subject?* That is `§0`'s "detector availability versus data sufficiency" stated as a line number.

The equivalent gate inside the detectors is `if (!ledger) return;` — sixteen occurrences covering 27
rules. A detector that returns early is indistinguishable, downstream, from one that ran and found
nothing. Both produce zero findings, and zero findings is read as compliance.

## 2. The model

One new result field. It is the whole design.

```jsonc
"inspected": {
  "subject": "project",              // or "framework" — whose property this result is about
  "state": "inspected",              // inspected | no-subject | unresolved-pointer
  "surfaces": [
    { "surface": "claims-ledger", "paths": ["artifacts/claims-ledger.md"], "declared": false }
  ]
}
```

**Surfaces are declared per rule and resolved per run.** A new module states, for each rule with a
detector, which evidence surfaces that rule reads. The CLI resolves each surface against the target
repository to a concrete list of repo-relative paths. The union of a rule's resolved paths is what
that rule inspected, and it goes into the result whether the rule passed or failed.

The surface vocabulary is small and closed, because a surface the framework cannot name is a surface
it cannot check:

| surface | resolves to |
| --- | --- |
| `claims-ledger` | the ledger named by `mathematics.claimsLedger`, if it exists |
| `proof-sources` | proof-assistant files found in the scan |
| `open-problems` | `problem.md` records under `mathematics.openProblemsDir` |
| `project-policy` | `project-policy.yml` |
| `prose` | scanned text files, excluding the framework's own standards documents |
| `references` | the reference block of the ledger |
| `declared:<rule>` | artifacts the adopter named for this rule (see §5) |
| `framework-home` | the framework's own installed artifacts — **subject `framework`** |

`state` is derived, not authored:

- **`inspected`** — at least one surface resolved to at least one path. The rule may pass, fail, or
  warn exactly as it does today.
- **`no-subject`** — every surface resolved empty. The rule becomes `skipped / not-evaluated`,
  carrying a reason that distinguishes it from *no detector exists*. This is `§0`.
- **`unresolved-pointer`** — the adopter declared an artifact for this rule and it does not resolve.
  **Fail-closed** (§5).

### Three decisions, and why

**A rule with no subject is `not-evaluated`, not `failed`.** `§0` says this explicitly and it is
right: a project that has not yet written a claims ledger should see *nobody checked*, not a red
build for every claim rule. The distinction from "no detector exists" is carried in the reason
string, not in a fourth disposition — inventing one would break every consumer switching on
`disposition`, to record something the reason already says.

**`no-subject` leaves the score's denominator, exactly as `not-evaluated` already does.** No new
scoring rule; the existing one does the right thing once the status is right. Scores will move, and
that movement is the acceptance signal, not a regression.

**`subject: "framework"` is recorded, and in this step changes nothing else.** `§0h` says the
requirement is not to exclude these rules — the framework auditing its own integrity during an
adopter's run is useful — but that a result must say whose property it is about. Whether a
framework-subject result belongs in an *adopter's* score is a real question and it is deferred to
step 5, where it can be decided against a measurement instead of a guess. Recording the subject is
what makes that measurement possible.

### The granularity constraint

Standing, from step 2's measurement onward, and binding on every surface added after it:

> **A surface must identify the semantic subject a detector actually examines, at the granularity of
> that examination — not merely the file containing it.**

`literature.resolvable-identifiers` is the case that earned it. Surfaced against the ledger *file*,
the rule reports as having inspected something in every repository that has a ledger. Surfaced
against the *identifiers*, it reports 0 in both frozen adopters — which is what §0 says it is doing.
A rule can have a subject and still have examined nothing of the kind it checks, and only the finer
granularity can tell those apart.

The constraint has a cost worth naming: a surface resolver that models what a rule reads can drift
into restating what the rule decides. The line is that a resolver may count *candidates* — things of
the kind the rule examines — and must never apply the rule's judgement to them.
`reference-identifiers` counts references carrying a DOI or arXiv token; whether such a token is
*well-formed* is the rule's business, and the resolver does not ask.

### The resolution tri-state

A resolver returns one of three answers, never a bare array:

```text
resolved-nonempty   the surface was read and held things
resolved-empty      the surface was read and held nothing      ← an observation
unresolved          the surface could not be read              ← not an observation
```

Collapsing the last two is exactly the `cited-artifacts` defect: a resolver reading four key names
the parser never produces returned `[]` for every entry in every repository, and the output said
"inspected no artifacts" about a ledger citing dozens. **Observed empty and resolver-failed are
different propositions**, and a field that collapses them cannot be audited — the same objection this
milestone raises against the framework's passes. The distinction becomes load-bearing at §0m, where a
declared pointer that does not resolve must fail closed.

A rule is `no-subject` only when *every* surface is `resolved-empty`. One `unresolved` surface makes
the rule `unresolved`, which step 4 prices.

### What this is not

It is not a claim that the framework read the mathematics. `inspected` records which files a
detector's evidence came from; it says nothing about whether the check is any good. A rule that reads
the right file and applies a bad regex will now say so precisely — which is an improvement over
saying nothing, and is not assurance.

## 3. The four claims, as tests, before implementation

Red first. Each claim is a property of the output, not of an implementation.

**C1 — a PASS names the project evidence it inspected.** A rule that passes over real evidence
carries a non-empty `inspected.surfaces` with resolved paths. A rule with nothing to read does not
pass at all.

**C2 — wrong-root evidence cannot satisfy an adopter rule.** Pinned as a cross-root pair, both
directions, per the sequencing note below:

```text
framework HOME has valid evidence, adopter does not  →  the adopter must not PASS
adopter has valid evidence, framework HOME does not  →  the adopter may PASS
```

Both directions are required. The first alone is satisfiable by breaking the rule; the pair is
satisfiable only by moving the subject of evaluation from framework-global state to project state. A
changed path constant passes the first and fails the second.

**C3 — an accepted pointer must resolve to and inspect its target.** A declared artifact that does
not exist fails closed. A declared artifact that exists is *read*: the syntactic presence of the
pointer never satisfies the rule on its own.

**C4 — `audit` declares whether a verdict was computed.** See §6.

Each red test must fail against `03f44d6` for the stated reason, and the reason is recorded beside it
— a test that fails because a fixture is malformed proves nothing about the claim.

## 4. `§0e` — the recorded mechanism is wrong, and the correction belongs here

The candidate says the validator does not report the current digest, citing all three output
surfaces. **Measured against the frozen RH specimen, that is not what happens.**

| surface | occurrences of a current attestation digest |
| --- | --- |
| human render (`validate`) | **14 of 14** |
| `status` | 0 |
| `--json` | 0 |

RH has 14 attestations, all with `reviewedAgainst.paths`, none with a `digest`.
`attestationDigests` computes a digest for every one of them, and `standards.mjs` prints all 14 — in
the `else` branch, reached only when neither `--json` nor `--status` is set.

RH's own `project-policy.yml` records the opposite in a standing comment: *"the validator reports the
current digest; it does not, so there is nothing to copy."* The adopter measured from `--json`. They
were right about their own observation and wrong about the mechanism, and the recorded consequence —
14 permanently-fresh attestations — is exactly as real either way.

**The correction makes the defect more clearly this milestone's.** It is not that the digest is never
computed or never shown. It is that a value which exists, is correct, and is the documented way to
opt into staleness detection is emitted on exactly one of three output surfaces — and not the
machine-readable one. That is a visibility defect in the same family as `§0`, `§0h` and `§0m`, and it
is why `§0e` is in this milestone rather than beside it.

The candidate entry will be corrected in place with the measurement, not rewritten: a mis-stated
mechanism whose consequence held is itself evidence about how these defects get found.

### As built — the endpoint is every surface, not the model

The first implementation stopped at the model: `reviewedAgainst.currency` is `verified-current` or
`unknown`, `currentDigest` is carried beside it, and `--json` reports both. That repaired two
surfaces of three and left `status` saying nothing, which is this defect in miniature — the
framework knowing something correctly and one supported surface not saying it. `status` is the
one-screen summary an agent reads before deciding whether a human review still stands, so it is the
worst of the three to omit: a human-reviewed pass nobody can date reads there as an ordinary pass.

The phrase is derived in one place, `currencyPhrase`, and the count in `unknownCurrency`, so the
three surfaces cannot drift apart again. They render differently on purpose — JSON carries a field,
the two text surfaces carry a phrase — and the property is not that they match but that **none of
them lets an attestation of unknown currency read as a current one**.

`unknown` is stated as a word rather than left to be inferred from a null digest. A reader who has
to derive the consequence from two nullable fields will read the fresh-looking one as fresh, which
is how fourteen attestations came to be permanently current in the first place.

**The falsifier is one test over all three surfaces**, not three tests. Three would let a surface be
dropped and the suite stay green everywhere except in a file nobody edited. Mutation-checked in both
directions: deleting the currency from `renderStatus` fails it naming `status`, and deleting it from
the human render fails it naming the human render. Both were reverted.

Measured after the change, both frozen specimens: RiemannHypothesis `BLOCKED_BY_INVARIANT` / 88 and
PvsNP `NON_COMPLIANT` / 97, unchanged. RiemannHypothesis's `status` now reports **12 of 12
attestations of unknown currency** where it previously reported none — the twelve honoured ones; its
other two attestations are the rejected pair that block the run.

## 5. Pointers as a reusable primitive

`§0m` must not be repaired inside `lifecycle.failed-routes-preserved`. The primitive:

```js
resolveEvidencePointer(projectRoot, pointer)
  → { kind: "resolved",   pointer, paths: [...] }
  → { kind: "unresolved", pointer, reason }
  → { kind: "unsupported", pointer, reason }
```

`unsupported` is not a convenience. A pointer form the framework does not understand — a URL, a glob
it does not implement, a reference into another repository — must be reported as *not followed*,
never silently treated as absent (which would read as `no-subject`) and never as satisfied.

Where pointers come from: the adopter names them, per rule, in the policy. A declared pointer is a
positive assertion by the adopter that a specific artifact discharges a specific duty, and it is
therefore held to a higher standard than an absence:

```text
declared and resolves      → the detector reads the named artifact
declared and unresolved    → FAIL (fail-closed). The adopter asserted an artifact that is not there.
declared and unsupported   → FAIL. The framework must not claim to have followed what it cannot read.
not declared               → fall back to the existing heuristic, unchanged
```

The fail-closed cases are failures rather than `no-subject` for a reason worth stating: `no-subject`
is the honest report when nobody claimed anything. Here somebody did.

> **Overruled at step 4, and the original is left standing so the change is visible.** The table
> above makes an unresolvable pointer a FAILURE. That is wrong, and wrong in the direction this
> milestone is supposed to be careful about: the framework could not reach the evidence, and being
> unable to look is not an observation about what would have been seen. The adopter may be entirely
> compliant and have mistyped a path. `failed` asserts the framework knows which, and it does not.
>
> What survives is *fail-closed*: the rule cannot PASS. What changes is that it also cannot FAIL. See
> §11 for what it does instead, and for the escape hatch that decision opens.

**A pointer's existence must never satisfy the rule.** This is the specific defect `§0m` records —
`lifecycle.failed-routes-preserved` passes on a `###` heading in `problem.md` while blind to PvsNP's
1,283-line `docs/FAILED_ATTEMPTS.md`. Replacing "guess from the path" with "accept whatever is
declared" would reproduce the defect with better manners.

## 6. `audit`'s contract, decided rather than drifted

`audit` emits findings and no verdict. **That is intentional and stays**, on the evidence of the
framework's own design: `renderHuman` ends with *"This is evidence, not a verdict. Run
`math-standards validate` for a compliance status."* The separation is the point — observations and
conclusions are different artifacts, and collapsing them would undo a distinction this framework
exists to draw.

The defect is that the intent is stated **only in the human render**. `audit --json` emits
`{schemaVersion, repo, auditedAt, findings}` and nothing that says a verdict was not computed. A
consumer that receives it has no field distinguishing *"audited, no verdict"* from *"evaluated, and
nothing to report"*. An empty `findings` array reads as a clean bill of health.

So: make the declaration machine-readable and unmistakable, in both directions.

```jsonc
{ "schemaVersion": "1.0.0", "repo": "...", "verdict": null, "verdictComputed": false,
  "note": "Audit only — no compliance verdict was computed. Run `validate` for one.", "findings": [] }
```

Additive; `schemaVersion` unchanged, on Tier 1's reasoning — the format versions on incompatible
change, and a new field breaks no consumer joining on `findings`.

## 9. Standing test rule, carried out of Tier 1

Tier 1 found a test asserting "the prose arm must not block" that passed against a run returning
`NOT_EVALUATED` — it counted blockers, and zero blockers is what a verdict-less run has. The
assertion was true and vacuous.

> **No acceptance assertion may rely solely on an aggregate count when it can name the rule and the
> status directly.** Counts are permitted in addition to a named assertion, never instead of one.

Recorded in `design/testing-principles.md`. It is broader than this milestone and it is stated here
because this milestone is where it will next be violated: every claim in §3 is naturally expressible
as a count, and a count is exactly what a `no-subject` state changes for reasons unrelated to the
claim under test.

## 11. Step 4 as built — resolution semantics, and one consequence

Split as the brief asked: resolution semantics first, score consequences not at all. The rule:

> A detector may accept an evidence pointer only if the framework can resolve that pointer to the
> artifact the detector actually intends to inspect.

### The measurement `§0m` deserved and did not have

`lifecycle.failed-routes-preserved` looks for a preserved record of abandoned work by matching path
*shapes*: `/(^|\/)(abandoned|failed|dead-ends?|attempts?)(\/|$)/i`, which requires a whole path
segment to be one of those words. Both frozen adopters keep exactly the record the rule wants:

| adopter | artifact | matched by the heuristic |
|---|---|---|
| RiemannHypothesis | `Research/FAILED_APPROACHES.md` | no |
| PvsNP | `docs/FAILED_ATTEMPTS.md` | no |

`FAILED_ATTEMPTS.md` is not the segment `attempts`. The rule passes in both repositories on its
other arm — a `###` heading in some `problem.md` — so in 2 of 2 adopters the framework's proxy is
blind to the real artifact and reports a pass anyway. `§0m` is not a hypothetical about this rule; it
is its measured behaviour, and the pass has nothing to do with the thing the rule is about.

### The primitive

`scripts/pointers.mjs` — `resolveEvidencePointer(projectRoot, pointer)` → `{ pointer, target, kind,
status, reason }`, `status ∈ resolved | missing | unsupported | invalid`, `target` project-relative
with forward slashes, `reason` null exactly when resolved. Reading the artifact is the caller's job:
a primitive that judged the contents would be a detector.

Two invariants, both earned:

1. **The project root is a parameter with no default, and a missing one throws.** Every wrong-root
   defect in this audit is a check that resolved something against whichever root was nearest —
   usually the framework's, because that is where the process runs. A defaulted parameter is how
   that happens. A symlink leading out of the project is `invalid` for the same reason.
2. **Four statuses, not two.** They collapse to one `unresolved` at the rule, because the verdict
   does not need four new outcomes. The diagnostic keeps them apart, because the remedy differs: a
   missing target is the adopter's to fix, an unsupported form is the framework's.

### The policy key

```yaml
artifacts:
  failedRoutes: docs/FAILED_ATTEMPTS.md
```

Semantic, not detector-specific. `lifecycleFailedRoutesPreservedPath:` would tie the adopter's
vocabulary to the framework's current rule ids, which change; `failedRoutes` says what the artifact
*is*, so any rule needing a record of abandoned routes can ask for it. One class, because that is
what the evidence requires — a registry larger than that is a vocabulary nobody has tested.

Declaring is opt-in and never makes a rule apply that otherwise would not. Both frozen adopters
declare nothing, and the undeclared surface resolves to observed-empty, which blocks nothing.

### Required surfaces, rather than rule-level contagion

`inspectionFor` gained `unresolved: [names]` and `blocked: boolean`; a declaration gained
`requires: [...]`. **A result is invalidated only when a surface the rule requires is unresolved.**
Rule-level contagion overstates the damage — a rule whose secondary arm is unresolved while its
primary arm fully establishes the result *has* been evaluated, and calling it incomplete is its own
false statement. `assertSurfacesKnown` refuses a `requires` entry the rule does not read, because
such a requirement can never fire: a fail-closed guard that fails open.

### What `unresolved` produces

```text
resolved, and the target records routes    → PASS
resolved, and the target records nothing   → FAIL  (the framework looked, and looked at the right file)
declared, and does not resolve             → skipped / not-evaluated, inspected.state = unresolved
not declared                               → the existing heuristic, unchanged
```

The middle case is the one the brief was conservative about and the conservatism is right. It uses
the status the framework already has for *evaluation could not establish this*; it invents no
fourth disposition; and the pointer's own classification stays in the diagnostic. Three renderers now
run unconditionally in the ordinary `validate` output, and the new one is the sharpest of them: these
rows are `skipped`, the quietest status the report has, and what they report is that the project said
where its evidence was and the framework failed to reach it.

```text
  Could not be evaluated — declared evidence did not resolve
    lifecycle.failed-routes-preserved
      declared record of abandoned routes — missing: 'docs/FAILED_ATTEMPTS.md' does not exist under …
```

### The escape hatch this opens, stated rather than left to be discovered

An adopter that would FAIL this rule can declare a pointer to a file that does not exist and move
from `failed` to `skipped / not-evaluated`. That is a better-looking result obtained by naming a
file that is not there — `§0m`'s own complaint, one level up.

It is left open at step 4 on purpose, because closing it means deciding what an unresolved evaluation
costs, and that is step 5's question. It is recorded here, named in the render, and pinned by
`test/evidence-pointers.test.mjs` so it cannot be forgotten. The candidate closure: an unresolved
required surface may never yield a *better* outcome than the same repository with no declaration at
all. That is expressible as a comparison and needs no new status — but it is a scoring decision, and
scoring waits.

### Acceptance

`test/fixtures/artifact-key-attempts` and `artifact-key-approaches` reproduce the two adopters'
shapes: the same duty, the same semantic key, two different filenames in two different directories.
Neither matches the path heuristic and neither carries the `###` proxy, so a pass can only have come
from following the pointer. Both pass.

Both frozen adopters are unmoved, byte for byte: RiemannHypothesis `BLOCKED_BY_INVARIANT` / 89 /
`{passed: 59, failed: 7, warnings: 0, skipped: 16}`; PvsNP `NON_COMPLIANT` / 97 / `{passed: 51,
failed: 2, warnings: 0, skipped: 29}`.

## 12. Step 5 as built — what belongs in an adopter's score

Steps 2–4 made the evidence surface truthful. This step decides what truthful evaluation means for
aggregation. The governing property:

```text
score(with an unresolved required pointer)  <=  score(without the pointer)
```

and the same for terminal status. A project must never improve its report by naming an artifact
that is not there.

### The hatch, measured before it was closed

A fixture pair identical apart from one policy line — `artifacts.failedRoutes` pointing at a file
that does not exist:

| | status | score |
|---|---|---|
| `escape-hatch-undeclared` (one honest failure) | `NON_COMPLIANT` | 97 |
| `escape-hatch-declared` (same repo, pointer at nothing) | **`COMPLIANT`** | **100** |

Step 4 moved the rule from `failed` to `skipped / not-evaluated`, which was right about the rule and
wrong about the aggregate: `skipped` leaves the denominator entirely, so the repository's one real
failure vanished and the score rose. Naming a file that is not there bought full compliance.

### What changed

**Only `subject: "project"` results are scored.** Five rules — two `framework`, three `run` — are
outside the score and outside the status. An adopter cannot affect
`integrity.provenance-digest`; a row nobody being measured can change is not a measurement of them.
This is `§0h`'s consequence, and it is why RiemannHypothesis moves 89 → 88: it was being paid for
the framework's own integrity.

**A foreign failure is still reported, in `foreignFailures` and its own render block.** Excluding
these from the verdict must not discard them: `evidence.skipped-never-passed` failing means *this
tool misreported something*, which a reader needs even though it is not their repository's fault.
Both frozen adopters have none, and the field is present and empty rather than absent — an absent
key and an empty one are different propositions.

**Invariant blocking stays subject-independent.** `BLOCKED_BY_INVARIANT` is an instruction to stop,
not a property claim about the repository, and a future framework-subject invariant must still be
able to halt a run. None of the five is an invariant today, so nothing changes; the reasoning is
recorded because the code looks like an oversight otherwise.

**An unresolved required surface is a zero-credit denominator entry.** It occupies a slot and can
never earn it. This is what makes the score *fall* rather than merely fail to rise, and it is
preferable to restoring the failure: the framework still does not know whether the project preserves
its failed routes, and an unearnable slot says exactly that without claiming more. The rule's own
result keeps the status step 4 gave it, and a test asserts so — a future change that buys
monotonicity by re-failing the rule fails that test.

**An aggregate `unresolvedRequired` condition carries the terminal status.** A project that declares
where its evidence is and points at nothing has a defect in its records, and the framework will not
call that compliance. `blockedBy` stays empty; nothing here is an invariant.

**`notEvaluatedBecause` on every result.** Six values under one status, and the remedy differs for
each:

```text
no-detector          nobody implemented a check          → an implementer
no-subject           there was nothing to inspect        → the project acquires the thing
unresolved-evidence  the declared artifact was unreadable → a corrected pointer
stale-attestation    what was reviewed is not what is there now → the same reviewer again
expired-attestation  the review lapsed                   → a renewal
not-applicable       declared out of scope, with a reason → nothing
```

The stale case is the one this exposed. Before it, a stale attestation reported *"No implemented
check evaluates evidence.discarded-failures"* — true of the detector and false about the history. A
person reviewed that rule, recorded what they read, and the file changed underneath them. It read
identically to a rule nobody had ever looked at.

The field is normalised in `summarise` rather than at each construction site, because four results
are hand-built and Tier 1 lost real time to a field added to `base` and forgotten on exactly those
four.

**The denominator is itemised.** `frameworkSubject`, `runSubject`, `noSubject`, `noDetector`,
`unresolvedRequired`, `staleAttestation`, `expiredAttestation`. "34 of 82" invites a reader to assume
the other 48 were merely unimplemented; they are five different things, and two of them are what
`§0h` and `§0m` are about. The human render prints the same itemisation as one `Outside:` line.

### Measured

| | before (6eadfe0) | after |
|---|---|---|
| RiemannHypothesis | `BLOCKED_BY_INVARIANT` / 89 | `BLOCKED_BY_INVARIANT` / **88** |
| PvsNP | `NON_COMPLIANT` / 97 | `NON_COMPLIANT` / 97 |
| `escape-hatch-undeclared` | `NON_COMPLIANT` / 97 | `NON_COMPLIANT` / 97 |
| `escape-hatch-declared` | `COMPLIANT` / 100 | `NON_COMPLIANT` / **97** |

Neither adopter's status moves. RH's score falls one point, entirely from losing five rules it was
never being measured on; PvsNP's is unchanged because the same five left both the numerator and the
denominator in a ratio that rounds to the same integer. The escape hatch is closed on both the score
and the status, and the two halves of the pair now agree — which is the property, stated as a
number: an unresolved declaration is worth exactly what a failure is worth, and never more.

## 13. Step 6 — score history, and where `integrity.*` belongs

### RiemannHypothesis 89 → 88 is not a regression

Recorded here and in the envelope, because a score is only meaningful against scores computed the
same way and this framework has now changed the way once.

RiemannHypothesis reads **89 under basis version 1 and 88 under version 2, from the same commit of
the same repository**, with no mathematics altered, no record edited and no rule newly failing. Five
rules that were never about that project left the denominator. The one point is the correction, not
a loss.

The envelope carries `scoreBasis: { id, version, since, note }`, and the contract is narrow on
purpose: **two scores are comparable when their `scoreBasis.version` agrees, and are not otherwise.**
The expensive half of the fix — restating historical numbers under the new basis — is not available,
because the old numbers were produced by code that no longer exists. Saying so is better than a
migration that would have to guess.

### The architectural question, settled from ownership rather than from convenience

`§0h` names four rules as "not about this project" and treats them as one category. Step 2 split them
into `run` and `framework`. The remaining question is whether the two `framework` rules should be
*relocated* to the adopter's root instead of merely labelled.

**`integrity.rule-lifecycle-honest` cannot be relocated, and this is not a judgement call.** Its
description is *"A rule is removed or weakened only via its `deprecatedIn`, `supersededBy` and
`removedIn` fields, together with a CHANGELOG entry and a MAJOR version bump"*, and the detector
iterates `CATALOG.rules`. Rules exist only in the standards pack. There is nothing at an adopter root
to point it at; a change that "fixed the root" here would be reading a directory that does not exist.
Pinned by a test, because an impossibility that is only obvious from the detector body will be
re-proposed.

**`integrity.provenance-digest` is the real question, and the catalog answers it.** The description
names a path without an owner — *"each file listed in `artifacts/provenance-digests.json`"* — so the
path alone does not settle anything. The rationale does: *"Fidelity checks a standard against the
spec, so the cheapest way to make a standard true is to edit the spec … The digests are the fixed
point that makes that edit fail."* The subject is the standards pack's own source documents, under
Standard 21, whose whole concern is a standard weakened to permit a conclusion. That is the
framework's housekeeping, and relocating the rule would export it as an adopter obligation.

The property that settles it, and which no path constant can fake — three adopter states:

| adopter's own `artifacts/provenance-digests.json` | framework-ownership reading | adopter-root reading |
|---|---|---|
| absent (`wrong-root-absent`) | result identical | varies |
| present and drifted (`wrong-root-broken`) | result identical | fails |
| present and correct (`wrong-root-clean`) | result identical | passes, in their score |

**Invariance across all three** is the framework-ownership reading stated as something testable, and
it is what the suite now asserts. The third fixture is the one that was missing: the drifted case
shows the adopter cannot be *punished* by a rule that is not theirs, and only the correct case shows
they cannot be *flattered* by one either.

### What separation still leaves owed, and where it goes

An adopter that keeps its own `artifacts/provenance-digests.json` has asserted something about its
own source documents, and nothing in this framework reads it. That is `§0m`'s complaint exactly — a
declared artifact the framework never opens — and it is **not** repaired by labelling.

But it is not repaired by relocation either. The missing thing is a proposition the catalog does not
contain: *the adopter's own recorded source documents are unmodified*. That is a new rule, not a
different root for an existing one, and adding a rule to the catalog is upstream's decision under the
same deferral discipline as `§0j` and `§0k`. Recorded here as a candidate, not taken.

What step 6 does instead is refuse the silence. The ordinary render now says, under the foreign-
subject block:

```text
    integrity.provenance-digest — passed, about the framework
      your artifacts/provenance-digests.json was not inspected; this row read the framework's copy
```

Framework-subject rows only. The first draft applied it to every foreign row and reported four of
RiemannHypothesis's own documents as uninspected — a run-subject rule's surfaces resolve to the
adopter's files, so the note was not merely noisy there but false, and precisely inverted.
