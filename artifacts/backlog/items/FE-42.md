## What

The claims-ledger grammar of Standard 3 lets an adopter cite a section of a document —
`proofs/clm-0002.md#base`, `formal/Squares.lean#sq_nonneg`, the form the shipped
`templates/claims-ledger.md:49-50` teaches. Four detector sites take that locator, cut it at the `#`,
and check only that the file exists. The rule then passes, and the envelope records the artifact as
inspected.

The property: a pointer naming a fragment is either resolved to that fragment and inspected there, or
reported unresolved. It must not be silently widened to the containing file and counted as resolved.

## Why

Measured on 2026-08-23 at `85b27b7`, on a copy of the `math-compliant` fixture with one character
changed — `proofs/clm-0002.md` became `proofs/clm-0002.md#no-such-section`, an anchor that appears
nowhere in that file:

| ledger cites | file exists | anchor exists | `evidence.artifact-linked` | verdict |
|---|---|---|---|---|
| `proofs/clm-0002.md#no-such-section` | yes | **no** | `passed`, `evaluated`, cited-artifacts 4 | `COMPLIANT` / 100 |
| `proofs/no-such-file.md#no-such-section` | no | no | `failed` | `NON_COMPLIANT` / 95 |

So the file arm works and the fragment arm is discarded. The rule reports it inspected four cited
artifacts when one of the four named a location that does not exist, and the envelope's
`inspected.surfaces` says `cited-artifacts: resolved-nonempty: 4`. That is a surface reporting
resolution it did not achieve, which is EP-07's subject rather than a missing capability.

This repository has already written down why the widening is wrong, in the module that refuses to do
it. `scripts/pointers.mjs:97-102` returns `unsupported` for a fragment and gives the reason: *a rule
told to inspect one section of a document and handed the whole document has not inspected what it was
pointed at.* Two surfaces of the same repository disagree about the same locator, and the careful one
is not the one adopters' ledgers go through — `resolveEvidencePointer` has exactly two callers
(`scripts/standards.mjs:1506`, `:2351`), both on the policy-declared failed-routes path. **No ledger
locator reaches it at all.** The earlier framing of this as "fragment resolution is unimplemented"
was wrong in the way that matters: the capability gap is real but harmless, and the false assurance
sits somewhere else.

## Notes

The four truncation sites, all `split("#")[0]`: `scripts/standards.mjs:1038` (computation evidence),
`:1320` (the Formal block's cited artifact), `:1561` (`evidence.artifact-linked`), `:2286` (the cited-
paths set feeding `inspected`).

A fifth site is inconsistent in the other direction: `scripts/standards.mjs:2293` matches
`entry.formal?.file` against the file set **without** stripping an anchor, so a Formal block whose
`file:` carries one is never counted as citing anything. Same locator, two spellings, opposite errors.

One consequence to weigh when designing this rather than after: `:1320` scans the whole file for
placeholder tokens when the ledger named one declaration. For that detector the widening over-fires
rather than under-reports — a `sorry` elsewhere in the file would be attributed to a declaration that
does not contain one. Narrowing to the anchor is the honest reading, and it makes that detector
strictly weaker; that is a trade this feature has to state, not discover.

Not started here, and deliberately not folded into FE-41. FE-41 is a verified release candidate at
`85b27b7` and its diff is closed; this is a second instance of the same kind found afterwards, and
it carries its own measurement and its own release boundary.

## Red-first design check, 2026-08-26

Measured on `main@8e77453` before any code changed. Five falsifiers, one per consumer; four red.

| | Property | Result on `main` |
|---|---|---|
| F1 | a nonexistent anchor is not reported resolved | **red** — `evidence.artifact-linked` passed, `COMPLIANT`/100 |
| F2 | a valid anchor resolves | green, for the wrong reason: the anchor is discarded |
| F3 | a placeholder outside the named declaration is not attributed to it | **red** — `BLOCKED_BY_INVARIANT`/96 with the target clean |
| F4 | `formal.file` uses the same locator semantics as evidence paths | **red** once isolated |
| F5 | no consumer widens `file#anchor` while reporting it inspected | **red** — surface byte-identical to unanchored |

**F4 first came back green, and that green was vacuous.** In `sorry-certified` the Evidence block
also cites `formal/Main.lean`, so the file entered the surface by a second route and the defective
site never showed. Removing that line isolates it: with an anchored `formal.file` as the sole
citation, the cited-artifacts surface drops from **1 path to 0** — a ledger citing one artifact,
reported as having inspected none. That is the §0 shape the comment at the call site warns about,
arriving through a spelling difference. The isolating fixture is now
`test/fixtures/formal-anchored-locator`, and B2 carries an assertion that fails if the second
citation route is ever restored.

An earlier harness also produced two vacuous greens from a lookup on `rule`/`result` where the
envelope uses `ruleId`/`status`. Every lookup in the committed tests now throws on a miss.

## Scope decision, 2026-08-26

**The five sites are not one semantic question, and were not forced through one abstraction.**

*Fixed.* `:2286` and `:2291` now both go through one primitive, `containingFile` in
`scripts/claims.mjs`, together with `:1038` and `:1561`. Four file-level consumers, one spelling
rule. This is the whole of the repair and it closes F4 and the asymmetry.

*Deliberately unchanged — `:1320`, the placeholder scan.* The item previously argued that narrowing
to the anchor "is the honest reading". **That was wrong, and the standard is why.** Standard 16 R5
does say the `Formal` block names a declaration rather than a file, which read alone favours
narrowing. But R3 defines the prohibited scope as a placeholder *"anywhere the target's proof depends
on"* — the dependency chain, which is neither the file nor the single declaration — and the rule's
own `$assuranceNote` states that it **does not trace the dependency graph**. Given that, the file is
a conservative over-approximation of the chain and the anchor is an under-approximation. Narrowing
would trade over-firing for missed violations on a `forbidden`, `nonExemptible` rule gating
`BLOCKED_BY_INVARIANT` — false assurance introduced by the fix, which is this epic's own subject.

What was actually wrong at that site was the *silence*, not the width. The finding now says the count
is over the whole file, that the chain is not traced, and that this does not establish the named
declaration contains or depends on a placeholder. `test/fixtures/formal-placeholder-elsewhere` makes
the conservatism testable, because a fixture whose `sorry` sits inside the named declaration cannot
detect the narrowing at all.

## F1 is preserved as a separate design conflict, not an acceptance test

**F1 is still red and is deliberately not fixed here.** `evidence.artifact-linked`'s published
description says the reference resolves *"with any anchor suffix removed before resolution"* — present
in `rules/evidence.json` since `168fcd3`, the commit that created the catalog, and therefore written
before the detector under the catalog-before-evaluator ordering. Standard 19 R3 requires only that
*"a path-shaped reference MUST resolve"*. So a nonexistent anchor in an existing file passes **by
contract**, not by accident.

The repository genuinely holds two positions: `scripts/pointers.mjs:97-102` refuses to truncate a
fragment and gives the reason — *a rule told to inspect one section of a document and handed the whole
document has not inspected what it was pointed at.* Reconciling them means **amending a published rule
description**, which is the same act that classified 3.0.0 as MAJOR, and it needs its own disposition
and release decision rather than riding in on a repair. Nothing in `test/anchored-locator.test.mjs`
asserts an answer either way; B5 asserts only that the two spellings agree with each other.
