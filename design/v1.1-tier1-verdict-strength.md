# Tier 1 design · A finding's evidence strength constrains the verdict it can produce

**Status: design. Nothing here is implemented.** `scripts/compliance.mjs` is untouched by this
document. It exists so the question is settled before central verdict logic is edited.

Scope is **§0b and §0i**, together, as one milestone. `§0c` is deliberately outside it: the engine
should stop treating weakly supported findings as certainty *before* a detector is asked to carry
the epistemic safety of the whole system.

**This design uses only evidence distinctions the engine already emits.** It introduces no evidence
basis, no reviewer kind, and no third applicability value. §0j and §0k are deferred upstream on
purpose, and a Tier 1 that quietly needed them would be a backdoor implementation of deferred work.
The only vocabulary used below is `label ∈ {OBSERVED, INFERRED, CONFIRMED_BY_OWNER, UNKNOWN}`, which
is validated today at [`standards.mjs`](../scripts/standards.mjs) in `evidence.labels`, and
`isInvariant(rule) = forbidden ∧ nonExemptible`, which exists today in
[`compliance.mjs`](../scripts/compliance.mjs).

---

## 1. What is actually broken

### 1a. The label never reaches the verdict

[`compliance.mjs:141`](../scripts/compliance.mjs):

```js
const outcome = level === "required" || level === "forbidden" ? RESULT.failed : RESULT.warning;
```

The outcome is a function of the **rule's level** alone. The finding's own `label` and `severity`
travel into the envelope, are rendered for a human, and are then discarded. `BLOCKED_BY_INVARIANT`
follows from `status === failed ∧ invariant`, so a regex over prose reaches the framework's terminal
conclusion by a path along which its own confidence was never consulted.

This is the RiemannHypothesis instance: `computation.evidence-as-proof`, five matches, all false,
`severity: warning`, `label: INFERRED`, and the run blocked.

### 1b. The label defaults to certainty

This is the PvsNP instance, and it is sharper than "a detector labelled itself `OBSERVED`".

[`standards.mjs`](../scripts/standards.mjs), the reporting helper:

```js
function report(rule, { message, evidence = [], label = "OBSERVED", severityOverride = null }) {
```

**`OBSERVED` is the default.** Of the report sites in the file, the large majority omit `label`
entirely and therefore inherit certainty. `claims.silent-promotion` is one of them — it never chose
`OBSERVED`; it declined to choose at all.

Worse, and this is the part that makes the fix structural rather than a one-line correction: **that
rule's two arms have different epistemic bases and share one default.**

| Arm | What it rests on | Honest label |
| --- | --- | --- |
| ledger arm | a `History` entry parsed out of the ledger, with no `evidence` field | `OBSERVED` |
| prose arm | a status word within 48 characters of a claim id, in running text | `INFERRED` |

Both currently report `OBSERVED`. The prose arm is the one that blocks PvsNP, on a sentence whose
second clause denies the status it is accused of asserting.

The docstring directly above the helper already states the correct rule — *"A detection resting on a
phrase match or a guess at a quantifier is INFERRED — reporting a heuristic as observed is the tool
fabricating certainty about its own output."* The doctrine is right and the default contradicts it.

### 1c. §0i is the same defect, reached through the parser

`parseObligation` defaults unrecognised text to `open`. So
`- **Obligations:** none — the claim is an implication and the implication is complete` becomes one
*open* obligation named `none — the claim is…`, which on a proved-rank claim is
`proof.complete-with-open-obligations`, an invariant.

The parse is a **guess**. A defaulting branch is an inference about text the grammar did not
recognise, and a finding resting on it is not an observation. The same is true of `parseHistory`
taking everything after the first comma as evidence: where the grammar is positional and the input
did not match, what follows is inferred.

So §0b and §0i are one milestone not because they feel similar, but because **both are findings that
report certainty they do not have, and both then reach a verdict nothing can clear.** One acquires
its false certainty from a default parameter, the other from a default parse.

## 2. The ceiling

> **A finding's evidence strength constrains the strongest verdict the engine may derive from it.**

The existing verdict order, unchanged:

```text
COMPLIANT  <  COMPLIANT_WITH_EXCEPTIONS  <  NON_COMPLIANT  <  BLOCKED_BY_INVARIANT
```

`NOT_EVALUATED` is outside this order and is untouched.

**Verdict ceiling.** The cell is the *maximum* consequence the engine may derive; a rule whose level
is lower still lands lower.

| Finding label | Rule kind | Strongest consequence |
| --- | --- | --- |
| `OBSERVED` | invariant | **`BLOCKED_BY_INVARIANT`** |
| `OBSERVED` | ordinary | `NON_COMPLIANT` |
| `INFERRED` | invariant | `NON_COMPLIANT` |
| `INFERRED` | ordinary | `NON_COMPLIANT` |

**The only special elevation is `OBSERVED` + invariant.** Everything else that fails, fails
ordinarily. Stated as a predicate rather than a table, the whole change is: *the elevation to
`BLOCKED_BY_INVARIANT` requires `label === "OBSERVED"` in addition to the conditions it requires
today.* That is one conjunct, it is explainable in a sentence, and it invents no evidence model.

### `INFERRED → NON_COMPLIANT` means: actionable failure, not unwaivable certainty

This is the heart of the milestone and it should be read as a definition, not a severity choice.

```text
NON_COMPLIANT           the run fails, the finding stands, and the project has a
                        permitted move: fix it, or file an exception with a reason.

BLOCKED_BY_INVARIANT    the run fails and there is no permitted move at all —
                        no exception, no attestation, no applicability declaration.
                        It asserts that the violation is certain.
```

`INFERRED` lands in the first because a heuristic is entitled to demand attention and not entitled
to assert certainty. The ceiling is emphatically **not** `warning`: a capped finding still fails CI
and still appears in every report. The defect was never that the run failed. It was that a
scrupulous project had **no permitted move**, because Standard 21 prohibits the only two that
remained — editing honest prose, or editing the framework.

### The two unused labels

`CONFIRMED_BY_OWNER` and `UNKNOWN` are in the validated label set and no detector emits either.
**Neither elevates.** The elevation predicate is exactly `label === "OBSERVED"`, so the table above
is total without a row for them.

`CONFIRMED_BY_OWNER` is the arguable one — a human confirmed it, so it looks at least as strong as
`OBSERVED`. It is left non-elevating deliberately: nothing produces it today, and assigning
blocking power to an unused label would be deciding what a human confirmation is worth, which is
inside the territory §0l defers. When something emits it, that is the evidence to decide on.

### What must not change

- `BLOCKED_BY_INVARIANT` remains absolutely unclearable when it is reached. **The fix is upstream of
  the block, never a softening of it.** A weakened invariant would be the Standard 21 manipulation
  arriving through the front door.
- **No finding is deleted, silenced, or downgraded in severity.** The ceiling changes the *verdict
  composition*, not the finding list. A capped finding is still reported, still `error` severity if
  the rule says so, and — per §3 — is marked as awaiting adjudication rather than quietly demoted.

## 3. Label integrity

The ceiling is worthless if a heuristic can still call itself `OBSERVED`. Three requirements, in
increasing order of how much code they touch.

**R1 · `report()` requires `label`. There is no default at all.**

> **No finding acquires evidentiary certainty through a default.**

That is the acceptance rule for the whole milestone, and it is pinned before implementation
deliberately. Not "the default becomes `INFERRED`" — *no default*. A missing label must fail fast,
loudly, at the call site. Flipping a default from one value to another moves the hidden assumption
in the opposite direction and leaves the mechanism intact: the next detector still gets its
epistemic status decided by a function signature written months earlier.

The ~53 call sites are not incidental work. Classifying them **is** the audit this milestone exists
to force — the first time anyone will have asked, per detector, *what is this resting on?*

**R2 · A finding whose evidence is a prose span is `INFERRED`, structurally.** Not by the detector
author remembering. The distinction available today is already in the evidence: a hit that cites a
parsed ledger field is different in kind from one citing a line of running text. Where a rule has
two arms, they report separately with separate labels — `claims.silent-promotion` becomes the
worked example, and its ledger arm must keep blocking.

**R3 · A finding resting on a defaulting parse is `INFERRED`, and the message says what was
parsed.** `parseObligation` reaching its fallback branch is an inference, and the finding it feeds
must carry that. This is also §0i's second requirement from the candidates file: *"One open
obligation named `none — the claim is…`" is a diagnosable message; "1 open obligation" is not.*

R3 is where §0i is fixed, and it is fixed by the same mechanism as §0b rather than by a special
case.

## 4. Predicted effect on the two frozen specimens

Stated as predictions **before** implementation, so the implementation can be judged against them
rather than described by them.

| | Now | After |
| --- | --- | --- |
| **PvsNP** `claims.silent-promotion`, prose arm, Cook–Levin sentence | `OBSERVED` (defaulted) → `BLOCKED_BY_INVARIANT` | `INFERRED` (R2) → capped at `NON_COMPLIANT`; finding retained, flagged for adjudication |
| **PvsNP** `computation.error-bounds-stated`, CLM-0021 | `INFERRED`, non-blocking failure | unchanged — it was never the block, and §0c is out of scope |
| **PvsNP** aggregate verdict | `BLOCKED_BY_INVARIANT` | `NON_COMPLIANT`, 2 findings, same 2 findings |
| **RH** `computation.evidence-as-proof`, prose arm, 5 matches | `INFERRED`, `warning` severity → `BLOCKED_BY_INVARIANT` | capped at `NON_COMPLIANT`; 5 findings retained |
| **RH** other blocking rules (3 total) | — | must be re-measured; only the prose-arm one is predicted to move |
| **Both** ledger-arm silent promotion, if present | blocks | **still blocks** |

**The aggregate verdicts are expected to change and that is the correct outcome, not a regression.**
What must not change is the finding list. If a specimen loses a finding, the implementation
suppressed detection instead of constraining composition, and it is wrong.

### 4a. Revision to the RH row, made before the run

The row above left RH's other two blockers unmeasured, and the call-site pass measured them. It did
not merely fill the gap — it falsified the assumption underneath the row, which was that every
blocker is a detector finding carrying an evidence label. Two of RH's three are not:

| RH blocker | Origin | Label | Predicted |
| --- | --- | --- | --- |
| `agent.refusal-on-invariant` | rejected attestation | `null` | **still blocks** — a human's recorded review is not weaker evidence than a regex |
| `formal.statement-overclaim` | rejected attestation | `null` | **still blocks**, same reason |
| `computation.evidence-as-proof`, prose arm | detector finding | `INFERRED` | caps to `NON_COMPLIANT`, `cappedFrom` set |

So the revised aggregate prediction is: **RH remains `BLOCKED_BY_INVARIANT`**, with `blockedBy`
going from three entries to two, and all seven findings retained.

That is a better specimen than the original row would have produced. PvsNP shows the ceiling
releasing a verdict that a heuristic should never have reached; RH shows it declining to release
one that a human reviewer did reach. A change that made both specimens green would be indifferent
to the distinction the milestone exists to draw.

It also fixes the cap condition. `label !== "OBSERVED"` would have capped both of RH's attestation
blockers, because `null !== "OBSERVED"`. The ceiling must key on an explicit non-elevating detector
label — `INFERRED` or `UNKNOWN` — and an absent label must leave existing behaviour untouched.
Tier 1 does not own the evidence semantics of result paths it did not create.

## 5. Acceptance tests

Each is written to be checkable against the two frozen specimens, unchanged: `RiemannHypothesis` at
`ec543d2` and `PvsNP` at its `standards-adoption` branch.

```text
1. Weak evidence cannot create an absolute block
   - an INFERRED finding against an invariant rule yields NON_COMPLIANT, never
     BLOCKED_BY_INVARIANT
   - holds for every invariant rule in the catalog, not just the two observed

2. Strong evidence still can
   - an OBSERVED finding against an invariant rule still yields
     BLOCKED_BY_INVARIANT
   - the ledger arm of claims.silent-promotion is the worked case: same rule,
     same run, one arm blocks and one does not

3. Downgrading the false block does not silence the finding
   - the capped finding appears in audit output, in validate output, and in the
     JSON, at unchanged severity
   - the JSON records that it was capped and why: the verdict it would have
     produced, and the label that prevented it
   - a run whose only finding is capped still exits non-zero

4. Genuine invariant violations remain blocking
   - the existing fixture "an observed violation of an invariant produces
     BLOCKED_BY_INVARIANT" passes unchanged
   - "no exception clears an invariant" passes unchanged
   - a planted OBSERVED violation of each invariant rule blocks

5. Both frozen adopters report the same underlying findings
   - PvsNP: exactly 2 findings, the same 2, before and after
   - RH: the same finding count and the same rule ids, before and after
   - aggregate verdicts may change; finding lists may not

6. Label integrity is not bypassable
   - report() cannot be called without a label (or defaults to INFERRED)
   - no detector resting on a prose match emits OBSERVED
   - a defaulting parse produces INFERRED and a message naming what it parsed
   - non-vacuity: at least one detector still legitimately emits OBSERVED
```

Test 3 is the one that catches the wrong fix. The tempting implementation — make the prose arm stop
matching — satisfies 1, 2, 4 and 5 and fails 3, because the finding disappears. **The correct fix is
in verdict composition, not in detection.**

### The three mutation tests, and what each would catch

Written as mutations because an acceptance test that only ever sees the correct implementation
cannot tell you it is testing anything.

**M1 · Verdict ceiling.** One synthetic finding against one invariant rule, emitted twice, differing
in nothing but its label.

```text
INFERRED + invariant  →  finding retained  →  NON_COMPLIANT
OBSERVED + invariant  →  finding retained  →  BLOCKED_BY_INVARIANT
```

Both assertions carry the finding-retention clause, so the test cannot be satisfied by suppressing
detection. *Catches:* an implementation that drops capped findings, and one that ignores the label.

**M2 · Detector basis.** The prose arm and the ledger arm of `claims.silent-promotion` must declare
*different* evidence bases. A fixture exercising both must produce one `INFERRED` finding and one
`OBSERVED` finding from the same rule in the same run. *Catches:* labelling the whole rule
`INFERRED` to make PvsNP pass — which would also stop a genuine unevidenced promotion from blocking,
trading a false positive for a false negative in the same rule.

**M3 · Parser uncertainty.** Feed `parseObligation` unrecognised text. The result must be explicitly
marked as unrecognised rather than silently defaulted into `open`, and any finding resting on it
must not be `OBSERVED`. *Catches:* fixing §0i by extending the grammar to accept
`none — <explanation>` while leaving the next unrecognised spelling to be manufactured into a fact.

**M4 · The default guard, against the easiest wrong implementation.**

> Changing the default label of `report()` globally must not be sufficient to make the suite pass.

Concretely: with the ceiling in place but every call site still unclassified, M2 must fail. This is
what forces the per-site audit rather than a one-character fix, and it is the mutation most likely
to be attempted, because it makes both frozen specimens go green in a single edit.

---

## 6. Implementation order

1. R1: make `label` mandatory in `report()`; fix the ~53 call sites, one judgement each. Mechanical,
   reviewable, and no behaviour change until step 3.
2. R2/R3: split `claims.silent-promotion` into two labelled arms; label the defaulting parse paths
   and make their messages name what was parsed.
3. The ceiling in `compliance.mjs`, with the capped-finding record in the envelope.
4. Re-run both specimens; compare against the §4 predictions and record every divergence.

Steps 1 and 2 are where the epistemic work is. Step 3 is small — the ceiling is a lookup — and it is
the last thing to write, not the first.
