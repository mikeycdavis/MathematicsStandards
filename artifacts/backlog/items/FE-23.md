## What

Give relevance a field, so it stops being recorded in prose beside a status that cannot express it.

## Why

The only affirmative addition the disposition accepted. Replicated in two different shapes: RH's category key 0/1/2/3 orthogonal to the fifteen-status ladder, and PvsNP reaching the same conclusion independently under kind-versus-strength pressure on EQUIVALENT_REFORMULATION ranked below LEMMA.

## Notes

It qualified because two adopters hit one field doing two jobs from two directions, and both had to record the second axis in prose because no field takes it.

Implemented on branch tier3-semantic-consistency, unmerged. `Relevance:` is parsed and carried in the envelope beside status; an optional policy-declared `relevanceScale` constrains membership and nothing else. The framework imposes no scale, because the disposition says RH's 0/1/2/3 encoding is project apparatus and only the distinction generalizes. `STATUS_RANK` is untouched and nothing that ranks reads the field.

Two things a later reader should not misread. The new rule `claims.relevance-vocabulary` is `required`, which under this repository's own versioning rule makes the eventual release **MAJOR** — the level was chosen from what the rule is, not from what version number it would produce. And **neither frozen specimen can evidence this item**: both froze before the field existed, so both satisfy the independence property trivially. Its evidence is fixtures, and the independence guard was strengthened only after a mutation test showed the first version passing a coupling it should have caught.
